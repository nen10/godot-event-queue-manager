# EQM 拡張依頼 (EBS 実需要) — DRAFT v2

> Status: **draft v2 — 相談ラウンド1 (2026-07-05) 反映済み、引き渡し可能**。
> EBS のスキル要素モデル (`SKILL_ELEMENT_MODEL.md`) の解決仕様ブロックと、
> 状態・関係システムの EQM 拡張決定を、EQM 側へ引き渡せる依頼形式に
> 起草したもの。EQM リポジトリは本リポジトリから read-only のため、
> この文書が引き渡し原本。EQM 側では applicative case への追加 +
> open questions registry への新規 Q + roadmap 項目化を想定している。
> 残る形式化課題は**メタレベル** (末尾) のみで、これは EQM 側設計と
> EBS 側相談の継続点として明示してある。

## 前提と責務の線引き

- EQM の既存契約 (v1.1) を前提とする: 決定的全順序 `(due_tick, priority,
  sequence)`、event-line (進行入力) と master timeline (解決順) の分離、
  L2 予約 (`IMMEDIATE/PREPARED/REACTION_PREPARATION/WAIT/READY/OPERATION`)、
  solve AND / invalidation OR / NAMED_PREDICATE、反芻 (`rumination`)、
  `EQTransaction` rollback、composite (SEM §7)、window (SEM §8)。
- 責務: **EQM 拡張** = 状態・関係の管理と解決順序・トリガの意味論。
  **ゲーム側** = 空間述語 (視界・範囲・座標) と効果の実行。
  **EBS** = スキル記述と型検査 (この依頼の語彙で解決仕様を宣言する)。
  空間条件を NAMED_PREDICATE としてゲーム側から供給する形は、感知分類を
  simulation 側 data とした EQM 既決 (Q12) の延長にある。
- 種別ラベル: **[新規]** 新規拡張 / **[確認]** 既存機能で表現可能かの
  適用確認 (受け入れ例の確定が成果) / **[相談]** 意味論が未確定で EBS 側
  ユーザー判断か EQM 側設計が必要。

実需要スキルの参照は `docs/application-needs/pre-concepts_full-scale-sim/`
(効果仕様・スキル一覧) に基づく。

## A. 状態・関係システム (新規サブシステム)

### R01 [新規] event-line 族の上の状態代数

- **依頼の核 (抽象)**: event-line の族に対する小さな代数構造の導入。
  1. **双対 (involution)**: 状態型に対合 `inv` を定義できる
     (`inv(inv(s)) = s`)。付与・解除・効果の意味論が `inv` を通して
     系統的に反転する。
  2. **前進規則の一時差し替え (suspension)**: event-line の前進規則を
     決定的な区間だけ停止・変更できる演算。
  3. **寿命の合成**: 状態の解除条件を既存の invalidation (OR) の語彙で
     束ねられること。
  実装が厳密に抽象的である必要はなく、以下の実需要が満たせれば十分。
- **実需要 (インスタンス例)**: 反転ペア 欠損⇄虚飾・狭窄⇄透徹・束縛⇄奔放・
  鈍化⇄機敏 (= `inv` の具体例)。凍結の保存・停止 (= suspension)。
  スタック系 (欠損, 反撃反芻) とターン系 (鑑別, 運命改変) の2種の寿命、
  現象 (ターン経過で解除されない) (= 寿命の合成)。
- **EQM 現状**: event-line が「名前つき整数進行変数」なので、ターン
  カウントダウンとスタック数は event-line / COUNTER でそのまま表現できる
  見込み。上記の代数 (双対・差し替え・合成) が未定義。
- **注意**: 個別ゲーム固有のスタック機構として解釈されないよう、EQM 側では
  抽象構造として設計し、EBS のスキル群は acceptance のインスタンスとして
  添える。

### R02 [新規] 関係グラフ

- **実需要**: 月 (主) / 星 (従) の有向関係。分類は追跡・求心・公平 + 反転
  (復讐の追跡反転)。維持条件 (視界系述語、付与条件)。構造は
  ツリー (召喚・身代・吸収)、ループ許容グラフ (解析)、直列/並列の合成。
  解消時の結び直し (解体:「直列関係の間ならば隣り合う関係を結び直す」)。
- **EQM 現状**: 対応する構造なし。actor lifecycle (SEM §13) と
  invalidate_actor はあるが、actor 間の永続的な有向関係は消費者側任せ。
- **依頼**: 関係を first-class の直列化可能データとして管理し、
  維持条件の評価を決定的な sweep 点 (T開始時など) に固定する。
  視界などの空間述語は NAMED_PREDICATE でゲーム側から供給する
  (**相談4で確定**: EQM は評価タイミングのみ固定する)。
  関係の付与・解消・結び直し・反転が trace に記録されること。

### R03 [新規] 連鎖・波及

- **実需要**: 連鎖 = 状態のラッピング (解明の透徹連鎖、転回の波及連鎖・
  反転連鎖)。波及 = 効果対象の動的拡大 (鑑波の損害波及: 対象が召喚関係の
  星なら月にも同時に損害、泡撃の反射関係の波及的付与)。
- **EQM 現状**: 効果の対象集合は消費者側の関心で、EQM は順序のみ扱う。
  ただし波及が「同時」を要求するなら composite (SEM §7) に関わる。
- **依頼**: 関係グラフ (R02) を入力として「効果対象の展開規則」を解決
  パイプラインのどの段で評価するかの意味論。展開が再帰する場合の
  停止規律 (関係ループ時) を含む。

### R04 [新規/確認] オーラ・地点効果の時間意味論

- **実需要**: aura/MI (移動後に効果)、地点効果/T (T開始時)・/M (侵入・
  ダメージ時)・/S (スキル用途時)、1c/1T (回数・期間限定)、重複時の
  lv 上昇、寸断 (地点効果の誘発を防ぐ地点)。
- **EQM 現状**: トリガ条件 + event-line で時間・回数側は表現できる見込み。
  空間帰属 (どのマスか・侵入判定) はゲーム側。
- **依頼**: 「空間述語つき反応準備」の標準形を applicative case として
  確立してほしい (侵入時トリガ = ゲーム側述語 + EQM 反応準備、の合成例)。
  寸断のような「トリガ抑制」が invalidation で書けるかの確認を含む。

## B. 解決パイプラインの拡張

### R05 [新規] 介入による window 中終了とメタレベル

- **確定済み (相談1回答)**: 迎撃の反応タイミングは「相手の予約 (移動予約) が
  *解決され*、移動効果が起きた時」— つまり既存の解決時 sweep で足りる。
  発行時 sweep 点の新設は**不要**。
- **実需要 (新規部分)**: 迎撃を含むこの種の介入は、原則として**対象の
  window を中終了させる** (例: 移動 window の残りステップを打ち切る)。
  ただし**メタレベルに応じて window 終了を回避できる** (メタレベルの高い
  側の進行は打ち切られない)。
- **EQM 現状**: window (SEM §8) に「介入による中終了」と「終了可否を
  レベル差で判定する」意味論はない。
- **依頼**: window の中終了 (premature close) を介入の標準効果として定義し、
  介入側・window 側が持つメタレベルの比較で終了回避を決定的に判定する
  規律を導入する。メタレベルの形式化は末尾の継続相談点。

### R06 [確認] 反撃反撃ループの停止規律

- **実需要**: 執着「互いに反撃反撃ならば反撃不能になるまで (焦点コスト
  切れまたは HP=0 など) 反撃がループする」。
- **EQM 現状**: fired reaction は schedule され、その解決がまた sweep 点に
  なるので連鎖自体は表現できる。停止条件はゲーム側資源 (焦点コスト・HP) の
  NAMED_PREDICATE で書ける見込み。trigger nest の reentrancy は Q21 で
  既決 (SEM §8)。
- **依頼**: 相互反撃ループの golden trace を受け入れ例として追加し、
  「無限ループはコスト述語の閉包で必ず止まる」ことを acceptance で示す。

### R07 [新規] 効果書き換え介入 (対戦術) と発行連鎖メタデータ

- **確定済み (相談2回答)**: 対戦術は「対象イベントの効果そのものを特定の
  パターンに従って変更する効果」の一種で、書き換え後の効果 target は
  event 発行者を想定する (弱化反射 = 付与先を発行者に差し替える、
  損害反転 = 損害→回復の変換、のようなパターン適用)。
- **実需要 (追加の複雑さ)**: 操作系スキル効果 (EQM の window 系 event) を
  経由した event 発行に対する対戦術・反射は、効果の向かう先を
  **操作 root / 中間操作者 / 直接の発行者**のどれにするか調整できる要素と
  なる。調整可能な範囲は、対戦術・反射側の event と操作側の
  **メタレベル差**に応じる。
- **EQM 現状**: 解決サイクル (pop → effect → chunk → sweep → drain) に
  effect 変換の介入点がない。event に発行連鎖 (誰の操作を経由して発行
  されたか) のメタデータがない。
- **依頼**:
  1. 対象イベントの effect 適用に対する**パターン変換フック** (決定的な
     適用順序つき) の導入。
  2. event への**発行連鎖メタデータ** (操作 root … 中間操作者 … 直接発行者)
     の付与。ユーザーからは「event-line のメタデータ拡張が必要かも」との
     示唆あり — event / event-line どちらに載せるかは EQM 側設計判断。
  3. 変換後 target の選択規則をメタレベル差で決定的に定める (R05 と共通の
     メタレベル形式化に依存)。

### R08 [確認] 防御誘発スタックの順序付け

- **確定済み (相談5回答)**: 防御誘発スタックの実体は**ゲーム側**で持つ
  (枚数方式かダメージ量ブロック方式かという詳細もゲーム側管理)。
  EQM 拡張が持つのは処理順序の規律のみ。
- **実需要**: 同化「盾・反射・損害共有等の防御誘発スタックは、スタック内の
  スタック順で処理の優先順位を与える」。
- **EQM 現状**: 同時解決の上位順序は comparator hook (Q20, SEM §7.1,
  fallback=発行順) が拡張点として存在する。
- **依頼**: スタック順 comparator の適用例を受け入れ例化するのみ。

### R09 [確認] 公平関係の並列効果処理

- **確定済み (相談3回答)**: 「並列」= 同一 tick の composite として解決し、
  互いの結果を入力にしない (順序独立)。**その上で、state に反射等があれば
  個別に誘発する場合がある** — composite 解決後の個別 state トリガは
  通常の sweep で発火する、という二段構え。
- **実需要**: 審判の公平「元の関係と公平により増えた関係による効果処理は
  直列せず並列に行う」。
- **EQM 現状**: composite (SEM §7) が同時性の器としてそのまま使える見込み。
- **依頼**: 公平の受け入れ例 (視界条件の非対称、composite 解決 + 事後の
  個別反射誘発を含む) を golden trace 化。

### R10 [新規] 入れ子操作フェーズとループ解消

- **実需要**: OPERATION 系の深い入れ子。共鳴の4段階操作解決 (対象選択 →
  操作関係抽出 → 状態に基づく確定 → 操作処理)、鏡面 (水鏡) の再帰的
  追加入力フェーズと「操作フェーズ遷移がループするとき、最小のループ
  経路上全ての鏡面の入力を解除したフェーズに遷移する」。
- **EQM 現状**: OPERATION 種別と window nesting (SEM §8) はあるが、
  操作フェーズの再帰とループ検出・巻き戻しの意味論はない。
- **依頼**: 操作フェーズの入れ子を window の再帰として定義し、ループ検出時の
  解消規則 (最小ループの入力解除) を決定的に定める。`EQTransaction` の
  working-copy がフェーズ単位の巻き戻しに使えるかの検討を含む。

### R11 [確認] 蘇生・追加行動のターン付与

- **実需要**: 酔夢の仮想現実 (戦闘不能→T開始時に戦闘可能へ復帰) と
  運命改変 (T開始時に範囲内の指揮予約を奪い、実質複数回行動)。
- **EQM 現状**: READY 予約の発行 (`ready_reservation_for`) は公開されて
  おり、政策外のターン付与も予約発行として書ける見込み。指揮予約の
  「上書き」は既存予約の invalidation + 再発行で表現できる見込み。
- **依頼**: 蘇生復帰と追加ターンの受け入れ例化。「既にされている指揮予約は
  上書きする」の decisive な表現 (invalidate → issue が同一 sweep 内で
  原子的に見えること) の確認。

### R12 [確認] 発行時修飾 (枯渇反動)

- **実需要**: 枯渇反動 = 処理時間 ×1.5、反撃不可、予約行動遅延。
  束縛 (焦点コスト増加)・荷重 (移動コスト増加) など、状態が予約の発行
  パラメータを修飾するケース全般。
- **EQM 現状**: 解決時間・コストは発行側 (EBS/ゲーム) が計算して渡す
  データなので、修飾は発行前にゲーム側で適用すれば済む見込み。
  「反撃不可」は反応予約の発行拒否で、これも発行側の判断。
- **依頼**: EQM 側の変更は不要という理解の確認のみ (applicative case に
  一行あると親切)。

## 継続相談点: メタレベルの形式化

相談1・2 の回答で、**メタレベル**が R05 (window 中終了の回避可否) と
R07 (操作連鎖上の対象調整幅) に共通する新しい横断概念として現れた。
未形式化の点:

- メタレベルは何に付与されるのか (スキル宣言? 操作 window の入れ子深さ?
  介入の種別?)。EBS 側はスキルの解決仕様ブロックにメタレベル宣言を
  持つことになる見込みだが、値の決まり方が未定。
- レベル「差」の比較規則 (同値のとき・順序がつかないときの既定)。
- 発行連鎖メタデータ (R07) との関係 — 連鎖の各段がメタレベルを持つのか。

EQM 側の設計判断と EBS 側のゲームデザイン判断が絡むため、引き渡し後の
共同相談点として明示しておく。
